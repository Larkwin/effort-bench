I'm planning the data model for people and expenses, including how equal splits should distribute leftover cents based on trip order rather than selection order, and figuring out how strictly to validate amount input strings like "$1,234.50" versus malformed entries.

For computing cents I'll parse amounts by splitting on the decimal point to avoid floating-point errors, and for balances I'm thinking through a greedy settle-up algorithm that matches the largest creditor to largest debtor to minimize the number of transfers needed, keeping the whole thing deterministic.

I'm working through the color palette and contrast ratios for the design system—navy, signal red, cream, and teal-green need to pass accessibility checks for text and UI elements, with owed/owes balances colored neutrally rather than alarmingly since owing money between friends is meant to feel normal, not like an error state. I'm pairing a serif display font for headings and amounts with a sans-serif body font that supports tabular numerals, and sketching the two-column desktop layout (inputs on the left, settle-up/balances/expenses on the right) that collapses sensibly on mobile via DOM order.

For the settle-up panel I'm planning a navy card with white and peach-toned text for contrast, plus copy that reinforces the "owing is normal" principle, and empty states for when there's nothing to settle or everyone's already even. I'm being careful to escape names via DOM text content rather than innerHTML, and to preserve checkbox/payer selection state across re-renders rather than wiping it out — tracking previously checked people in memory so new people default to checked while existing selections persist. I'm also deciding to default the payer select to the first person rather than using an empty placeholder, since that's friendlier to how tests are likely to interact with the form, and settling on clearing form errors on next input rather than leaving them stale.
